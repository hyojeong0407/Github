# Design

> 이 문서는 `requirements.md`의 요구사항을 구현하기 위한 기술 설계 문서이다. 현재 단계에서는 코드를 작성하지 않고 시스템 구조, 모듈 책임, 데이터 흐름, 계산 경계, UI 구성, 검증 전략을 정의한다.

## 1. 설계 개요

### 1.1 설계 목표

PC와 모니터의 소비전력 및 사용 패턴을 입력받아 전력 사용량과 예상 전기요금을 계산하고, 계산 결과를 웹 대시보드로 시각화한다.

설계 시 다음 원칙을 우선한다.

1. 입력·검증, 계산, 분석, 요금 계산, 추천, UI를 분리한다.
2. 전력 계산 결과의 출처와 단위를 명확히 유지한다.
3. 전기요금 기준을 코드와 분리하여 변경 가능하게 한다.
4. UI가 아닌 순수 계산 모듈을 중심으로 테스트할 수 있게 한다.
5. 데이터가 부족하거나 요금 기준이 검증되지 않은 경우 이를 사용자에게 명확히 알린다.
6. Requirements에 정의되지 않은 기능은 임의로 추가하지 않는다.

### 1.2 권장 기술 방향

초기 구현은 다음 기술 조합을 우선 검토한다.

- Python: 계산 및 데이터 처리
- Streamlit: 웹 대시보드 UI
- Pandas: 기간별 데이터 처리 및 표 형태 데이터 관리
- Plotly 또는 Streamlit 지원 차트: 추이·장비별 시각화
- Python 테스트 프레임워크: 계산·검증·요금 모듈 테스트

최종 기술 선택은 Implementation Plan에서 확정하며, 다른 기술을 선택할 경우 Requirements 충족에 유리한 이유를 기록한다.

## 2. 시스템 구조

시스템은 다음 계층으로 구성한다.

`Input Layer → Data Processing Layer → Calculation Layer → Analysis Layer → Recommendation Layer → Dashboard UI`

### 2.1 전체 구성 요소

| 구성 요소 | 주요 책임 | 입력 | 출력 |
|---|---|---|---|
| Input Layer | 사용자 입력 수집, 필드별 기본 형식 처리 | UI 입력값 | 원시 입력 데이터 |
| Validation | 필수값, 범위, 자료형, 시간 형식 검증 | 원시 입력 데이터 | 검증 결과와 오류 목록 |
| Data Processing Layer | 입력 정규화, 장비 목록화, 기간 데이터 준비 | 검증된 입력 | 정규화된 분석 입력 |
| Power Calculation Layer | 전체 소비전력·일일·월간 전력량 계산 | 정규화된 입력 | 전력 계산 결과 |
| Electricity Bill Layer | 요금 기준 적용 및 예상 요금 계산 | 월간 사용량, 요금 설정 | 요금 계산 결과 |
| Analysis Layer | 기간별 추이, 장비별 비교, 사용 패턴 분석 | 전력·입력·기간 데이터 | 분석 결과 |
| Simulation Layer | 변경 사용시간 기준 재계산 및 비교 | 기존 입력, 변경 사용시간 | 시뮬레이션 결과 |
| Recommendation Layer | 입력·계산·분석 결과 기반 절전 추천 | 분석 결과, 규칙/모델 | 추천 목록과 근거 |
| Dashboard UI | 입력, KPI, 차트, 결과, 오류 표시 | 각 계층의 결과 | 사용자 화면 |

### 2.2 의존성 방향

- UI는 각 도메인 모듈의 공개된 입력·출력 계약만 사용한다.
- 계산 모듈은 Streamlit UI에 의존하지 않는다.
- 전기요금 모듈은 전력 계산 모듈의 내부 구현을 알지 않고, 표준화된 월간 사용량과 요금 설정을 입력으로 받는다.
- 분석 모듈은 화면 렌더링을 수행하지 않고 시각화에 필요한 데이터 구조만 반환한다.
- 추천 모듈은 계산 결과를 근거로 사용하며, 근거 없는 독립적인 추천을 생성하지 않는다.

## 3. 모듈 설계

권장 디렉터리 및 모듈 책임은 다음과 같다.

| 영역 | 책임 |
|---|---|
| `input` | 입력 필드 정의, 원시 입력 수집, 입력 모델 |
| `validation` | 자료형·범위·필수값·시간 형식 검증 |
| `power_calculator` | 전체 소비전력, 일일·월간 전력량 계산 |
| `electricity_bill` | 요금 기준, 누진구간, 기본요금, 전력량요금 계산 |
| `analyzer` | 장비별 비교, 기간별 추이, 사용 패턴 분석 |
| `simulation` | 사용시간 변경 시나리오 계산 및 비교 |
| `recommendation` | 절전 추천 규칙 또는 AI 연동, 추천 근거 생성 |
| `dashboard` | Streamlit 화면 구성과 결과 표시 |
| `data` 또는 `config` | 요금 기준 및 선택적 분석 데이터 관리 |
| `tests` | 각 모듈의 단위·통합 테스트 |

구체적인 파일명, 클래스, 함수 시그니처는 Implementation Plan에서 확정한다.

## 4. 데이터 모델

### 4.1 사용자 입력 모델

사용자 입력은 UI의 자료형과 분리된 정규화 모델로 변환한다.

| 필드 | 자료형 방향 | 필수 여부 | 설명 |
|---|---|---|---|
| `pc_power_w` | 양의 실수 | 필수 | PC 소비전력 |
| `daily_hours` | 0 초과 24 이하 실수 | 필수 | 하루 평균 사용시간 |
| `monthly_days` | 1 이상 31 이하 정수 | 필수 | 월간 사용일수 |
| `monitor_power_w` | 0 이상 실수 또는 장비별 값 | 필수 | 모니터 소비전력 |
| `monitor_count` | 0 이상 정수 | 필수 | 모니터 개수 |
| `start_time` | 선택적 시간 | 선택 | 사용 시작 시간 |
| `end_time` | 선택적 시간 | 선택 | 사용 종료 시간 |
| `usage_purpose` | 선택적 문자열 또는 열거값 | 선택 | PC 사용 목적 |
| `other_devices` | 선택적 장비 목록 | 선택 | 기타 장비와 소비전력 |

모니터별 소비전력을 지원하는 경우 단일 `monitor_power_w`와 장비 목록 중 하나를 표준 입력으로 선택하고, 두 방식을 혼용하지 않는다.

### 4.2 장비 모델

장비별 비교와 전체 소비전력 계산을 위해 장비를 다음 논리 필드로 표현한다.

- 장비 식별자
- 표시명
- 장비 유형(PC, 모니터, 기타)
- 단위 소비전력(W)
- 수량
- 데이터 출처(사용자 입력, 측정값, 예시값)

장비의 총 소비전력은 `단위 소비전력 × 수량`으로 계산한다.

### 4.3 계산 결과 모델

계산 결과는 UI가 직접 공식을 재계산하지 않도록 하나의 표준 결과 구조로 관리한다.

- 전체 소비전력(W)
- 일일 전력 사용량(kWh)
- 월간 전력 사용량(kWh)
- 계산에 사용한 입력 요약
- 데이터 출처
- 계산 기준 또는 버전
- 표시용 반올림 전 원시값

### 4.4 요금 결과 모델

요금 결과에는 금액뿐 아니라 적용된 기준을 포함한다.

- 예상 전기요금(원)
- 월간 사용량(kWh)
- 적용 요금 기준 버전
- 적용 기준일 또는 기간
- 기본요금
- 전력량요금
- 기타 요금 항목
- 누진구간과 해당 구간의 계산 근거
- 요금 기준 상태(검증됨, 예시, 미검증)

요금 기준이 없거나 검증되지 않은 경우 결과 상태를 함께 반환하여 UI가 확정값처럼 표시하지 않도록 한다.

### 4.5 분석 결과 모델

분석 결과는 시각화와 텍스트 요약에 공통으로 사용할 수 있어야 한다.

- 기간 단위(일·주·월)
- 분석 시작일과 종료일
- 기간별 사용량 목록
- 장비별 소비전력 목록
- 평균 사용시간
- 가장 많이 사용하는 시간대 또는 데이터 부족 상태
- 이전 기간 비교값 또는 비교 불가 상태
- 데이터 출처와 추정 여부

### 4.6 시뮬레이션 결과 모델

기존 조건과 변경 조건을 동일한 계산 경로로 계산한 뒤 차이를 산출한다.

- 기존 조건의 전력·요금 결과
- 변경 조건의 전력·요금 결과
- 절감 전력량
- 예상 절감 금액
- 절감률
- 결과 상태(절감, 증가, 동일, 계산 불가)

## 5. 계산 및 데이터 흐름

### 5.1 기본 분석 흐름

1. 사용자가 PC, 모니터, 사용시간, 사용일수를 입력한다.
2. Input Layer가 원시값을 수집한다.
3. Validation이 필수값, 자료형, 범위, 시간 형식을 검증한다.
4. 오류가 있으면 계산을 중단하고 필드별 오류를 반환한다.
5. 정상 입력을 정규화된 사용자 입력 모델로 변환한다.
6. Power Calculation Layer가 전체·일일·월간 전력량을 계산한다.
7. Electricity Bill Layer가 설정된 요금 기준으로 예상 요금을 계산한다.
8. Analysis Layer가 장비별·기간별 결과를 준비한다.
9. Simulation Layer와 Recommendation Layer가 필요한 결과를 계산한다.
10. Dashboard UI가 동일한 결과 모델을 KPI, 차트, 표, 추천 영역에 표시한다.

### 5.2 기본 전력 계산 규칙

다음 계산은 Power Calculation Layer만 수행한다.

- `전체 소비전력(W) = PC 소비전력(W) + 모니터 소비전력(W) × 모니터 개수`
- `일일 전력 사용량(kWh) = 전체 소비전력(W) ÷ 1000 × 하루 사용시간(시간)`
- `월간 전력 사용량(kWh) = 일일 전력 사용량(kWh) × 월간 사용일수(일)`

기타 장비가 초기 범위에 포함되면 전체 소비전력에 합산하되, 포함 여부와 입력 모델을 확정한 후 적용한다.

### 5.3 절감 시뮬레이션 흐름

1. 기존 입력을 변경하지 않고 보존한다.
2. 사용자가 변경 사용시간을 입력한다.
3. 변경 사용시간만 대체한 입력 모델을 생성한다.
4. 기존 입력과 변경 입력을 동일한 전력·요금 계산 모듈에 각각 전달한다.
5. 두 결과의 차이로 절감 전력량과 예상 절감 금액을 계산한다.
6. 기존 요금이 0이면 절감률을 계산 불가 상태로 반환한다.
7. 변경 결과가 기존보다 크면 `절감`이 아닌 `사용량 증가` 상태로 표시한다.

### 5.4 데이터 출처 처리

각 결과에는 다음 출처 중 하나를 표시한다.

- `user_estimate`: 사용자 입력을 기반으로 계산한 추정값
- `measured`: 실제 측정 데이터
- `example`: 예시 데이터

실제 측정 데이터가 없는 초기 버전에서는 사용자 입력 기반 추정값임을 헤더와 결과 영역에 표시한다. 예시 데이터는 실제 분석 결과와 시각적으로 구분한다.

## 6. 전기요금 계산 설계

### 6.1 모듈 경계

전기요금 계산기는 월간 사용량과 요금 설정을 입력받아 요금 결과를 반환한다. 전력 사용량을 계산하는 모듈과 전기요금 계산 모듈은 서로 독립적으로 교체·테스트할 수 있어야 한다.

### 6.2 요금 설정 구조

요금 기준은 코드의 조건문에 직접 작성하지 않고 설정 데이터로 관리한다. 설정 데이터에는 다음 정보를 포함한다.

- 요금 기준 식별자와 버전
- 적용 시작일과 종료일
- 대상 요금 유형
- 누진구간의 최소·최대 사용량
- 각 구간의 기본요금
- 각 구간의 전력량요금
- 기타 요금 항목과 계산 규칙
- 공식 출처와 검증일

### 6.3 계산 상태

요금 계산기는 다음 상태를 반환할 수 있어야 한다.

- `verified`: 공식 자료로 검증된 기준
- `example`: 예시용 기준
- `unverified`: 출처 또는 적용 기준 확인이 필요한 상태
- `unavailable`: 계산에 필요한 기준이 없는 상태

`example`, `unverified`, `unavailable` 상태에서는 UI가 금액을 실제 청구액으로 오해하지 않도록 안내 문구를 표시한다.

### 6.4 미확정 정책

다음 정책은 실제 요금 기준 조사 후 확정한다.

- PC 사용으로 증가한 전력만 계산할지 가정 전체 사용량과 합산할지
- 주택용 요금 유형의 구체적인 적용 범위
- 기본요금, 전력량요금, 기타 항목의 포함 범위
- 세금·할인·환경 관련 항목의 처리
- 단위당 반올림과 최종 원 단위 처리

## 7. 분석 설계

### 7.1 기간별 추이

초기 입력만으로 실제 시간별 사용량을 확보할 수 없는 경우, 기간별 그래프는 사용자 입력 기반 추정값임을 표시한다. 데이터가 있는 기간만 그래프에 포함하고, 데이터가 없는 기간을 0으로 임의 보정하지 않는다.

분석 단위는 일·주·월을 지원하도록 추상화한다. 분석 기간을 변경하면 Analysis Layer가 해당 기간의 데이터만 반환하고 UI는 반환값을 시각화한다.

### 7.2 장비별 분석

정규화된 장비 목록을 기준으로 장비별 총 소비전력을 집계한다. 장비 수가 가변적이므로 실제 입력된 장비만 표시한다. 장비별 비교에는 막대 그래프를 우선 사용하고, 각 값에 W 단위를 표시한다.

### 7.3 사용 패턴 분석

- 하루 평균 사용시간은 사용자 입력값 또는 계산된 평균값으로 표시한다.
- 가장 많이 사용하는 시간대는 시간대별 데이터가 있을 때만 계산한다.
- 이전 기간 대비 변화는 비교 대상 기간이 존재할 때만 계산한다.
- 필요한 데이터가 없으면 임의의 추정 결과 대신 `데이터 부족` 상태와 사유를 반환한다.

## 8. 추천 설계

### 8.1 초기 추천 방식

AI 외부 모델 연동 여부가 확정되지 않은 상태에서는 입력값과 계산 결과에 기반한 규칙 중심 추천을 기본 대체 방식으로 둔다. 추천 규칙은 입력·분석 결과의 특정 조건과 연결되어야 한다.

예시 규칙:

- 하루 사용시간이 긴 경우: 사용시간 단축 시뮬레이션을 제안한다.
- 모니터 수 또는 모니터 소비전력이 큰 경우: 미사용 모니터 절전·전원 차단을 제안한다.
- 장시간 미사용 조건이 있는 경우: 절전모드 또는 주변기기 전원 차단을 제안한다.
- 변경 사용시간 시뮬레이션에서 절감액이 계산되는 경우: 절감 전력량과 예상 절감액을 근거로 표시한다.

### 8.2 추천 결과 구조

각 추천은 다음 정보를 포함한다.

- 추천 제목
- 추천 설명
- 추천 근거가 된 입력 또는 분석값
- 기대 효과의 정량값 또는 정성적 설명
- 데이터 출처
- 확정값인지 추정값인지에 대한 상태

추천 효과를 계산할 수 없는 경우 예상 금액을 생성하지 않고 정성적 안내만 제공한다.

### 8.3 외부 AI 연동 시 제약

외부 AI 모델을 사용하는 경우에도 모델이 사용할 수 있는 입력을 현재 사용자의 정규화된 데이터와 계산 결과로 제한한다. 모델이 반환한 추천은 근거 데이터와 함께 검증하고, 계산 결과와 무관한 추천이나 검증되지 않은 절감액은 화면에 표시하지 않는다. 외부 모델 사용 여부와 실패 시 대체 동작은 구현 전에 확정한다.

## 9. 대시보드 UI 설계

### 9.1 화면 구성

대시보드는 다음 순서로 구성한다.

1. 헤더
2. 입력 패널
3. KPI 카드
4. 전력 사용량 추이
5. 장비별 소비전력
6. 사용 패턴 분석
7. 절감 시뮬레이션
8. AI 또는 규칙 기반 절전 추천
9. 계산 기준 및 데이터 출처 안내

### 9.2 헤더

헤더에는 서비스명, 현재 분석 기간, 데이터 기준을 표시한다. 사용자 입력 기반 추정 결과인 경우 `사용자 입력 기반 예상값`과 같은 상태를 표시한다.

### 9.3 입력 패널

입력 패널은 필수 입력과 선택 입력을 구분한다.

- PC 소비전력
- 하루 평균 사용시간
- 월간 사용일수(기본값: 30일)
- 모니터 소비전력 및 개수
- 선택적 사용 시작·종료 시간
- 선택적 PC 사용 목적
- 기타 장비 입력(범위 확정 시)

분석 실행 또는 입력 변경 시 모든 필수값을 먼저 검증한다. 오류가 있는 동안에는 이전의 유효한 결과를 유지하거나 결과 영역에 계산 불가 상태를 표시하는 정책을 구현 전에 확정한다.

### 9.4 KPI 카드

네 개의 KPI 카드는 동일한 표준 결과 모델을 사용한다.

- 월간 예상 전력 사용량(kWh)
- 월간 예상 전기요금(원)
- 하루 평균 사용시간(시간)
- 예상 절감 가능 금액(원)

각 카드에는 값, 단위, 데이터 상태를 표시한다.

### 9.5 차트 영역

- 기간별 전력 사용량: 일·주·월 선택이 가능한 Line Chart
- 장비별 소비전력: 장비별 W를 비교하는 Bar Chart
- 차트 데이터가 없으면 빈 차트 대신 데이터 부족 안내를 표시한다.
- 차트의 원본 데이터와 KPI의 계산 기준이 다르지 않도록 공통 결과 모델을 사용한다.

### 9.6 시뮬레이션 영역

변경 사용시간 입력 컨트롤과 기존·변경 결과 비교 영역을 배치한다. 기존값, 변경값, 차이값을 시각적으로 구분하며, 사용량이 증가하는 경우 `절감`으로 표시하지 않는다.

### 9.7 추천 영역

추천마다 추천 내용과 추천 근거를 함께 표시한다. 확정된 절감액과 추정 가능한 절감 효과를 시각적으로 구분한다.

## 10. 검증 및 오류 처리 설계

### 10.1 검증 순서

1. 필수값 존재 여부 확인
2. 숫자 또는 문자열 등 자료형 확인
3. 수치 범위 확인
4. 정수 여부 확인
5. 시간 형식 및 시간 관계 확인
6. 입력 간 논리적 일관성 확인
7. 검증 오류가 없을 때 정규화

### 10.2 오류 반환 구조

검증 결과는 전체 성공 여부만 반환하지 않고 필드별 오류 목록을 포함한다.

- 필드명
- 오류 코드
- 사용자용 메시지
- 오류 심각도

UI는 오류 필드 가까이에 메시지를 표시하고, 오류가 해소되기 전에는 잘못된 입력으로 새 계산 결과를 표시하지 않는다.

### 10.3 주요 예외

- PC 소비전력 또는 사용시간이 0 이하
- 하루 사용시간이 24시간 초과
- 월간 사용일수가 0 이하 또는 31일 초과
- 모니터 개수가 음수 또는 정수가 아님
- 숫자가 아닌 값
- 필수값 누락
- 시작·종료 시간 형식 오류
- 자정을 넘기는 시간 처리 미확정
- 요금 기준 누락 또는 미검증
- 이전 기간 또는 시간대 데이터 부족

## 11. 상태 관리 및 데이터 저장

### 11.1 초기 범위

초기 버전은 한 세션 안에서 사용자가 입력값을 변경하고 결과를 재계산하는 흐름을 우선 지원한다. 입력 상태와 계산 결과의 저장 범위는 Streamlit 세션 상태 등 기술 선택에 맞춰 Implementation Plan에서 확정한다.

### 11.2 영속 저장

이전 기간 비교와 기간별 추이를 장기적으로 지원하려면 입력 및 분석 결과의 영속 저장이 필요하다. 파일 또는 데이터베이스 저장 여부, 사용자 구분, 보존 기간은 Requirements의 데이터 저장 정책 확정 후 설계한다.

### 11.3 상태 일관성

입력값이 변경되면 이전 결과를 그대로 재사용하지 않고 입력값과 요금 기준 버전에 맞는 계산 결과를 생성해야 한다. 결과에는 사용된 기준과 데이터 출처를 함께 보관한다.

## 12. 오류 처리, 보안, 관측성

### 12.1 오류 처리

- 사용자 입력 오류는 사용자용 메시지로 처리한다.
- 계산 불가 상태와 시스템 오류를 구분한다.
- 요금 기준 파일 또는 데이터가 없을 때 확정 금액을 표시하지 않는다.
- 추천 모듈이 실패해도 전력·요금 계산과 기본 대시보드는 사용할 수 있어야 한다.

### 12.2 보안 및 개인정보

초기 입력값은 PC 소비전력과 사용 패턴 중심으로 취급하되, 저장 기능을 추가할 경우 사용자 식별정보와 사용 데이터의 보존 범위를 별도로 정의한다. 외부 AI 모델을 사용하는 경우 전송 데이터와 개인정보 포함 여부를 검토하고, 불필요한 개인정보를 전송하지 않는다.

### 12.3 관측성

계산 오류, 요금 기준 로딩 실패, 추천 생성 실패를 구분해 기록할 수 있어야 한다. 로그에는 사용자의 민감한 입력값을 불필요하게 포함하지 않는다.

## 15. 승인된 정책 결정 및 범위 제한

- **계산 범위**: 가정 전체 사용량이 아니라 PC와 모니터 사용으로 증가한 전력량만 계산한다. 월간 kWh를 독립 사용량으로 요금표에 적용하며, 화면에는 `PC 사용분 기준 예상 증가액`과 `실제 가정 청구액 아님`을 함께 표시한다. 가정 전체 사용량 입력은 요구하지 않는다.
- **출처 우선순위**: 표준 출처는 `measured` 실측값 > `manufacturer_estimate` 제조사/사용자 제공 추정값 > `user_estimate` 사용자 입력 추정값 > `example` 예시값이다. 계산 결과는 source/status를 보존하고 기본 입력은 기존 동작을 위해 `user_estimate`를 사용한다. 측정값을 임의로 생성하지 않는다.
- **입력 범위**: `pc_power_w`, `daily_hours`, `monthly_days`, `monitor_power_w`, `monitor_count`를 필수로 유지하며 시작·종료 시간과 목적은 선택이다. PC와 모니터 장비 목록을 유지하고 기타 장비는 이번 범위에서 제외한다.
- **요금 설정**: 외부 설정 `TariffConfig`에 source/version/effective period/status를 보존한다. 현재 `data/config.py`의 10원/kWh는 공식 단가가 아닌 `example` 설정이므로 예시 요금으로만 표시한다. 공식 최신 단가 검증은 보류한다.
- **표시 규칙**: 내부 원시 정밀도를 유지하고 화면은 kWh 소수 둘째 자리, W 필요 시 소수 둘째 자리, 시간 소수 첫째 자리, 금액 원 단위 정수 반올림, 절감률 소수 첫째 자리로 표시한다. 0원 분모는 계산 불가이며 사용량 증가는 음수 절감으로 숨기지 않는다.
- **확장 지점**: 실측 CSV 업로드·수집과 영속 저장은 구현하지 않고 향후 입력 확장으로 문서화한다.



원본 FR/NFR/US/TC ID는 변경하지 않고 사용자가 승인한 확장 기능을 별도 경계로 둔다.

### 16.1 상태 및 데이터 흐름

- 프리셋 계산은 `simulation.preset_hours`가 기존 `UserInput.daily_hours`를 받아 음수가 아닌 변경 시간을 반환한다. UI는 반환값을 변경 입력에 넣고 기존 `simulate`를 호출한다.
- 소비 단계는 `consumption_stage.py`의 `CONSUMPTION_STAGES` 설정 데이터와 `classify_consumption(monthly_kwh)`를 사용한다. UI는 `PowerCalculationResult.monthly_kwh`만 전달하며 공식을 복제하지 않는다.
- 추천은 기존 입력·전력·분석 결과 기반 규칙을 유지하고 `priority`와 표시 순위인 `rank`를 추가한다. 절감액은 계산 근거가 없으므로 생성하지 않는다.

### 16.2 경계 및 데이터 출처

단계 경계는 50, 100, 200, 300 kWh이며 마지막 구간은 상한이 없다. 월간 81.60 kWh 기본값은 `🌱 새싹`으로 분류된다. 단계 안내의 사용량은 사용자 입력 기반 추정(`user_estimate`)이다. `🌲 큰 나무`에는 사용량이 많다는 보조 설명을 표시해 좋은 의미로 오해하지 않게 한다.

## 17. 설계 검토 체크리스트

- [ ] 모든 FR 요구사항이 하나 이상의 모듈과 연결되어 있는가?
- [ ] 전력 계산과 전기요금 계산이 독립되어 있는가?
- [ ] 요금 단가와 누진구간이 설정 데이터로 관리되는가?
- [ ] 계산 결과에 단위와 데이터 출처가 포함되는가?
- [ ] UI가 계산 공식을 중복 구현하지 않는가?
- [ ] 입력 오류와 데이터 부족 상태가 구분되는가?
- [ ] 절감과 사용량 증가가 구분되는가?
- [ ] AI 또는 규칙 기반 추천에 근거가 포함되는가?
- [ ] 기간별 추이 데이터의 출처가 명확한가?
- [ ] 요금 기준의 버전과 검증 상태가 표시되는가?
- [ ] TC-001 ~ TC-014를 실행할 수 있는 구조인가?
- [ ] 구현 전 미확정 사항이 결정되었는가?

## 16. 구현 전 승인 조건

Design 단계에서 다음 조건을 확인한 뒤 Tasks와 Implementation Plan 단계로 진행한다.

1. 모듈 간 책임과 데이터 계약이 승인되어야 한다.
2. 기본 계산 공식과 절감 계산 규칙이 Requirements와 일치해야 한다.
3. 전기요금 기준의 데이터 구조와 검증 상태 처리 방식이 확정되어야 한다.
4. 기간별 분석 데이터의 출처와 저장 범위가 확정되어야 한다.
5. 추천 기능의 초기 방식과 실패 시 대체 동작이 확정되어야 한다.
6. UI 구성과 오류 표시 정책이 승인되어야 한다.
7. Requirements의 미확정 사항을 해결하거나, 명시적인 후속 결정 항목으로 등록해야 한다.
